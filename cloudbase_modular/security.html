Data Security & HIPAA Compliance

A technical and administrative reference for institutional compliance officers, hospital CIOs, IRB chairs, and research ethics committees. This document describes how ATLAS protects research data and patient health information in accordance with the Health Insurance Portability and Accountability Act (HIPAA), 21 CFR Part 11 electronic records and electronic signatures requirements, the UAE Personal Data Protection Law (PDPL, Federal Decree-Law No. 45 of 2021), ADHICS v2.0 healthcare information security standards, and applicable federal and international research data-protection standards. As ATLAS expands its global infrastructure to serve institutions across North America, the Middle East, and beyond, these controls apply platform-wide to all workspaces.

Technical Safeguard

Data Encryption

All patient health information (PHI) and research data stored by ATLAS is encrypted at rest using AES-256 (Advanced Encryption Standard, 256-bit key), the same standard mandated by NIST for protecting classified U.S. government information. Encryption is enforced at the storage layer — no unencrypted PHI is written to disk under any operational condition.

All data transmitted between end-user devices and ATLAS servers is protected by TLS 1.3 (Transport Layer Security, version 1.3), the current gold standard for in-transit encryption. TLS 1.2 connections are accepted for legacy client compatibility; TLS 1.0 and 1.1 are disabled globally. Cloudflare edge termination provides automatic certificate rotation and HSTS enforcement.

Encryption at Rest
AES-256-GCM
Firebase Realtime Database and Google Cloud Storage — server-managed keys with envelope encryption. No key material is accessible to application code.
Encryption in Transit
TLS 1.3 / TLS 1.2
Enforced on all API endpoints and the ATLAS web application. HSTS preload enabled. Cloudflare SSL/TLS mode: Full (Strict).
Database Encryption
Firebase RTDB + AWS DynamoDB
Firebase RTDB: Google-managed AES-256 at rest. AWS DynamoDB (assessment records, audit trail): AES-256 server-side encryption with AWS-owned keys. All data at rest is encrypted at the storage layer in both systems.
Object Storage Encryption
AWS S3 — SSE-S3 / SSE-KMS
All S3 objects are server-side encrypted at write time. Bucket policies block unencrypted PUT requests. KMS CMK available for regulated data.
Technical Safeguard · Cloudflare Workers

Edge Security & Proxy Architecture

All ATLAS traffic is mediated by a Cloudflare Worker deployed at the edge before any request reaches application servers or AWS infrastructure. This design eliminates the need for direct browser-to-Lambda communication, removes CORS exposure from the AWS API Gateway, and enforces a uniform security perimeter across every incoming request regardless of origin or client type.

The Worker performs four security functions on every request: rate limiting, security header injection, authenticated proxy forwarding, and geographic routing. These controls are enforced at the infrastructure layer — they cannot be bypassed by client-side manipulation, browser developer tools, or scripted requests.

IP-Based Rate Limiting
60 requests / minute / IP
Enforced at the Cloudflare edge using the Cache API as an ephemeral counter store. Requests exceeding the limit receive HTTP 429 with Retry-After: 60. Static assets (.js, .css, images, fonts) are excluded — CDN serves these before the Worker runs. Rate limiting fires before any routing logic, preventing client-side bypass.
Security Response Headers
HSTS · CSP · X-Frame · XCTO
Every HTML response includes: Strict-Transport-Security: max-age=31536000; includeSubDomains; preload, X-Frame-Options: SAMEORIGIN, X-Content-Type-Options: nosniff, and Permissions-Policy: microphone=(self). These headers are injected unconditionally — they cannot be stripped or modified at the application layer.
Authenticated Server-to-Server Proxy
/lambda-proxy/* → AWS Lambda
Browser calls /lambda-proxy/<path> on the same origin. The Worker reads the Firebase ID token from the Authorization header and forwards it in a server-to-server fetch to the Lambda Function URL. Lambda validates the token independently. The API Gateway endpoint is never exposed to the browser — no CORS configuration is required on the AWS side.
UAE Data Residency Routing
/lambda-proxy-uae/* → me-central-1
A separate proxy path routes UAE workspace writes to the AWS API Gateway in me-central-1 (Abu Dhabi). This path is called exclusively by the ATLAS data shim for workspaces with region: "UAE". Routing is enforced at the Worker level — UAE data cannot be misdirected to the US endpoint regardless of client-side state.
US Lambda Endpoint
AWS Lambda · us-east-1 (N. Virginia)
Handles: API key validation, Firebase token verification, workspace provisioning, superadmin operations, and all non-UAE assessment writes. Accessed via Worker proxy path /lambda-proxy/*. Function URL is not publicly resolvable from the browser.
UAE Lambda Endpoint
AWS API Gateway · me-central-1 (Abu Dhabi)
Handles all database reads and writes for UAE-region workspaces (MMAS-8, MAP, PEACS assessments, audit log). DynamoDB tables reside exclusively in me-central-1 and are not replicated. Accessed via Worker proxy path /lambda-proxy-uae/*.
www → Apex Redirect
HTTP 301 · Permanent
www.atlas.adherence.cc is permanently redirected to the apex domain at the Worker level. Prevents split-identity phishing vectors and ensures HSTS and certificate coverage applies to a single canonical origin.
Module Cache Policy
no-cache on /modules/*.js
JavaScript modules under /modules/ are served with Cache-Control: public, max-age=0, must-revalidate to prevent browsers from serving stale module code after a security patch or compliance update. CSS assets use long-lived immutable caching.

Technical & Administrative Safeguard

Access Controls

ATLAS enforces role-based access control (RBAC) across all workspaces. Each authenticated user is assigned one of seven discrete roles — Student, Pharmacist, Researcher, Principal Investigator, Institution, Admin, or Spectator — with data visibility and write permissions scoped strictly to that role. Cross-role data access is blocked at the Firebase Security Rules layer, not merely at the UI layer.

Every write, export, login, and administrative action generates an immutable audit log entry timestamped to the nearest second and associated with the authenticated user's UID. Audit records are retained for a minimum of six years in accordance with HIPAA's documentation retention standard (45 CFR §164.530(j)). Logs are not editable by any user role, including platform administrators.

Authentication
Firebase Authentication (Google)
Email/password with optional email-link (passwordless) sign-in. Session tokens are short-lived (1 hour) with silent refresh. No credentials stored client-side.
Authorization Model
7-tier RBAC + workspace isolation
Access rules are enforced server-side via Firebase Security Rules. Each workspace is a siloed data subtree; cross-workspace reads are prohibited.
Audit Logging
Append-only, UID-attributed
All data writes, exports, and administrative actions are logged with event type, actor UID, timestamp (ISO 8601), and affected record references. Stored in atlas-audit DynamoDB table (me-central-1) with TTL auto-expiry after 90 days for operational entries; long-term records omit TTL for permanent retention.
Retention of Audit Records
6 years minimum
Complies with 45 CFR §164.530(j). Operational audit records use DynamoDB TTL (90-day rolling window); compliance-grade records are written without TTL for permanent retention. Cold-storage archive at 90-day intervals.

Administrative Safeguard

Data Retention Policy

ATLAS retains research data and PHI in accordance with HIPAA's minimum retention standards and applicable federal research data requirements. The following retention periods are enforced by default:

PHI / Assessment Records
6 years from creation
Per 45 CFR §164.530(j). Active records are retained in Firebase; records older than 3 years are archived to cold storage with continued encryption.
Audit Logs
6 years minimum
Audit records are append-only and cannot be deleted by any user role. Archived to mirrored cold storage at 90-day intervals.
Research Study Data
Per IRB protocol (typically 7 years)
Principal Investigators may configure per-study retention periods in alignment with their IRB-approved protocol. Default is 7 years post-study-closure.
Data Deletion Requests
30-day processing window
Participant data deletion requests are processed within 30 days. Audit log entries referencing deleted records are anonymized (UID removed), not deleted, to preserve audit integrity.

Institutional partners may negotiate custom retention schedules as part of their data processing agreement. Contact compliance@adherence.cc to initiate a data processing addendum.

Administrative Safeguard

Incident Response

In the event of a suspected or confirmed breach of unsecured PHI, ATLAS follows a documented Incident Response Plan in compliance with the HIPAA Breach Notification Rule (45 CFR §§164.400–414). The following timeline governs the response process:

Immediate — Detection & Containment (0–24 hours)
Suspected breach flagged via automated monitoring or user report. Affected systems isolated. Initial scope assessment conducted. Privacy Officer notified within 4 business hours of detection.
Short-term — Risk Assessment (1–10 days)
Formal risk assessment performed to determine whether the incident constitutes a reportable breach under the HIPAA four-factor test (nature of PHI, unauthorized person, acquisition/viewing determination, mitigation extent). Affected record count and identity of data subjects established.
Individual Notification — Within 60 days of discovery
Affected individuals notified by written notice (first-class mail or email where prior authorization exists) per 45 CFR §164.404. Notice includes description of the breach, types of PHI involved, steps individuals should take, and contact information for questions.
HHS Notification — Within 60 days (or annual log if <500)
Breaches affecting 500 or more individuals in a state or jurisdiction: HHS notified within 60 days of discovery and prominent media notice provided. Breaches affecting fewer than 500 individuals: logged and reported to HHS annually (no later than 60 days after end of calendar year).
Post-Incident Review
Root cause analysis documented. Security Rule policies updated as needed. Workforce training refreshed where applicable. Institutional partners notified of corrective actions taken. Full incident report retained for six years.

To report a security concern or suspected breach: compliance@adherence.cc. Response guaranteed within one business day.

Data Sovereignty & Regional Compliance

Data Residency — UAE & PDPL

As part of ATLAS's global infrastructure expansion, UAE-region workspaces store all patient records, adherence scores, and audit logs in the AWS me-central-1 region (Abu Dhabi, UAE) — ensuring data never leaves the United Arab Emirates. This architecture satisfies the data localization requirements of the UAE Personal Data Protection Law (PDPL, Federal Decree-Law No. 45 of 2021), DOH Data Privacy Standard, and ADHICS v2.0 (Abu Dhabi Healthcare Information & Cyber Security) for healthcare and research institutions operating in the UAE.

ATLAS uses a workspace-aware dual-proxy architecture: every assessment write is routed through the ATLAS data shim layer, which calls the appropriate Cloudflare Worker proxy path based on workspace region. UAE-region workspaces are directed to /lambda-proxy-uae/ → AWS API Gateway me-central-1 (Abu Dhabi); all other workspaces use /lambda-proxy/ → AWS Lambda us-east-1. Geographic routing is enforced at two independent layers: the client-side data shim and the Cloudflare Worker — UAE data cannot reach the US endpoint regardless of application-layer state. No application-level configuration is required from institutional users; residency is enforced automatically based on the workspace region attribute.

The following DynamoDB tables reside exclusively in me-central-1 and are never replicated to other AWS regions:

atlas-assessments
MAP & MMAS-8 Submissions
Every MAP Tri-Domain and MMAS-8 assessment record. Partitioned by workspace key; GSI on patient number for longitudinal lookups.
atlas-peacs
PEACS Assessment Records
Full PEACS submission records including PE scores and dimension source data. Same key pattern as atlas-assessments.
atlas-peacs-dim
Current Dimension Scores
Live Base / Movement / Strata dimension scores per patient. One row per patient+dimension; overwritten on each KYBOS submit (SET semantics).
atlas-audit
Immutable Audit Trail
All admin and clinician actions. Append-only; TTL auto-expiry on operational records (90 days). Compliance-grade entries written without TTL for permanent retention.

All DynamoDB operations are executed by an AWS Lambda function fronted by an API Gateway HTTP endpoint (me-central-1). The browser never communicates with DynamoDB directly — all reads and writes are mediated through Lambda, which enforces Firebase authentication, workspace isolation, and rate limiting before any database operation is performed.

Institutions in the UAE requiring a Data Processing Agreement (DPA) under PDPL may contact compliance@adherence.cc.

These tools are aligned with ADHICS v2.0 (Abu Dhabi Healthcare Information & Cyber Security Standard, version 2.0), UAE PDPL, and HIPAA requirements simultaneously.

  • Data Subject Access Request (DSAR) ToolPlatform Built Administrators can search all workspace records by patient number or email, preview all data held on that individual, export a structured JSON package for subject access requests, and anonymise records in place — replacing identifiers with irreversible SHA-256 hashes.
